Что добавлено:

4. В чек-листе отдельно зафиксировано правило пилота: клиенту ничего не отправляется и задачи не создаются без подтверждения эксперта.

3. Открыть карточку сделки → вкладка `ИИ-ассистент`.

# MAVIS Bitrix Expert Assistant — v46 правильный фикс Wazzup Telegram + короче комментарий

После прогона v45 нашлось две вещи:

1. **Комментарий в сделке всё ещё длинный.** Сократил ещё: убран блок «Из звонка понял» (он дублирует саму запись звонка), «чего не хватает» и «риски» объединены в один список без повторов (максимум 4 пункта), план действий — максимум 4 пункта. Итог — компактный рабочий отчёт, а не протокол.
2. **Моя правка Wazzup Telegram в v45 была неправильной.** По официальной документации Wazzup (`POST /v3/message`) для Telegram Personal `chatId` нельзя просто заполнить телефоном вручную — это поле приходит только из вебхука входящего сообщения или из ответа Wazzup на предыдущую отправку. Для исходящего сообщения, когда `chatId` неизвестен, нужно использовать поля `phone` или `username` — именно для этого они и существуют. В v45 я по ошибке заставил код всегда пихать телефон в `chatId`, что и вызывало `HTTP 500 / MESSAGES_CAN_NOT_ADD`. Возвращена правильная схема: `chatId`, если он есть → иначе `phone` → иначе `username`.
3. Добавлена одна автоматическая повторная попытка отправки, если Wazzup вернул HTTP 5xx — у них это документированная как `MESSAGES_CAN_NOT_ADD` временная ошибка сервера, повтор с новым `crmMessageId` часто помогает.

## v45 фикс после первого реального теста

После первого прогона автопилота на ООО «Бобик» нашлись 4 проблемы, все исправлены:

1. **Огромный комментарий в сделке.** Убрана полная расшифровка звонка из текста комментария (она и так есть в активности звонка). Комментарий теперь короткий: статус, передача, что понял, чего не хватает, риски, что делает дальше сам, стадия.
2. **Ассистент ставил задачи людям вместо того, чтобы исполнять самому.** Это было прямой ошибкой v44 — система создавала Bitrix-задачи Кристине и даже специалисту клиента (!). Полностью убрано создание задач (`tasks.task.add`) из автопилота. Теперь план из ИИ-анализа просто перечисляется в отчёте как «что ассистент делает дальше сам» — без постановки задач сторонним людям.
3. **Анализ шёл по неправильному продукту (СПК+АТТ вместо реальной услуги сделки).** В v44 продукт был захардкожен в коде (`'СПК + Аттестация организации (единый маршрут SPK_ATT)'`) и было жёсткое тестовое правило, которое заставляло ИИ считать «фасады» ошибкой, даже если клиент в звонке сам их подтвердил. Оба хардкода убраны: теперь продукт берётся из реального поля «Услуга» в Bitrix (`getService(deal)`), а виды работ ассистент определяет из звонка как они есть, без навязанных правил.
4. **Wazzup Telegram падал с HTTP 500.** Причина: для Telegram сервер отправлял нестандартное поле `phone` вместе с `chatId`, которого нет в официальной схеме `/v3/message` — Wazzup мог не обрабатывать эту комбинацию. Теперь для Telegram, как и для остальных каналов, используется только `chatId` (телефон цифрами), `username` — лишь как запасной вариант без телефона. Также улучшено логирование ошибки: если Wazzup возвращает пустое тело при ошибке, теперь видно реальный HTTP-статус и сырой текст ответа, а не пустые `{}`.

## v44 ассистент-исполнитель (полный цикл SPK_ATT)

Что изменилось в v44 (переход от помощника с подтверждением к исполнителю по слайдам теста):

1. Автопилот теперь делает всё за один клик по кнопке «Автопилот АТТ: звонок → ход работы»:
   - проверка передачи из продаж (используется существующая логика `checkHandoff`), при критичных пробелах — автозадача менеджеру, без остановки автопилота;
   - поиск и расшифровка записи первичного звонка (как раньше);
   - ИИ-анализ по единому маршруту **SPK_ATT** (СПК + аттестация организации вместе);
   - отправка хода работы / перечня клиенту через канал из поля сделки (как раньше);
   - **создание внутренних дел** (документы/оплата/дедлайны/следующий шаг) — теперь снова включено, но дела ставятся только сотрудникам MAVIS (`expert`/`manager`/`leader`), никогда клиенту;
   - **движение стадии сделки** — ИИ принимает решение `stage_decision` (двигать/не двигать и куда), код подбирает реальную стадию воронки динамически по названию через `crm.dealcategory.stage.list`, двигается только вперёд по воронке и только при явном решении ИИ; угадывания нет — если подходящей стадии не нашлось, стадия не меняется и это фиксируется в отчёте;
   - финальный комментарий Кристине фиксирует все 6 шагов: передачу, звонок, сообщение клиенту, внутренние дела, стадию, риски.
2. Ограничение пилота прежнее: работает только по `EXECUTOR_TEST_DEAL_ID`.
3. Запуск всё ещё кнопкой (без автотриггера по webhook) — это сознательное решение для текущего теста.

Переменная новая (опционально): `EXECUTOR_LEADER_ID` — кому ставить дела с ответственным `leader`. Если не задана, используется `EXECUTOR_EXPERT_ID`.
